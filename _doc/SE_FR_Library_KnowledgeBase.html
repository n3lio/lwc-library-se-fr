About — design principles, reading a component page

Why this library

⚡️

Faster demos

Drop a vetted component on a page, configure via App Builder, demo in minutes — not days.

✨

Prettier demos

Easy wow. Components are visually polished — subtle animations, consistent palette, design care — so your demos go beyond the raw Lightning standard.

🧩

Stay generic

Every component is industry-neutral. Customize via properties, not by editing code.

🤝

Share & contribute

One pool of components owned collectively by the SE France team.

Design principles

  • Lightning base components first. lightning-card, lightning-button, lightning-datatable & co. are translated by the platform — we use them wherever possible.
  • Custom strings become properties. Anything that could reasonably need renaming is an @api with a French default.
  • Demo data as JSON / CSV props. Dashboards with mock KPIs accept those as stringified JSON / CSV so SEs can swap the dataset in App Builder.
  • Currency & locale exposed. currencyCode (default EUR) and localeTag (default fr-FR) are properties.
  • Standard fields first. The library uses only Salesforce standard fields by default. No mandatory custom field.
  • Schema-safe Apex. Where an optional custom field can enrich the UI, Apex checks for its existence before referencing it — deploys succeed regardless.
  • Bilingual FR / EN. Every component exposes a language prop with FR/EN dictionaries baked in.

Reading a component page

Each component page carries:

  • Name — human name displayed in the App Builder master label. Example: Account Health.
  • API name — technical LWC identifier in camelCase. Example: seFrAccountHealth.
  • Tagline — one-line pitch, what you’d use to sell the component in 5 seconds.
  • Chips — 3-4 wow features. Examples: SVG donut gauge, Native drag & drop, 4 chart styles.
  • Status badges — labels at the top of the page. Examples: ● Stable, ✨ New, 🤖 AI-ready, 📱 Mobile-ready, No Apex.
  • Personas — target teams. Examples: 📌 Sales, 🚗 Field Sales, 📞 Service, 🤖 Agentforce.
  • Targets — page types where the component can land. Example: Home · App · Record.
  • Objects — supported SObjects on Record Pages. Examples: Account, Contact / Lead / Account, Any.
  • Apex — optional Apex dependencies, local or shared. Examples: SE_FR_AccountHealthController, SE_FR_ImageFileController (shared), none.
  • Data mode — how the component behaves towards org data. Values: live (reads/writes real records), hybrid (real if present, else mock), mock (100% prop-driven, no org dependency).
  • Pitch — short paragraph that fleshes out the tagline.
  • SE benefit — the demo angle that lands, the moment the prospect looks up from their screen.
  • Configurable settings — 3-5 key props to tune in App Builder. Examples: chartStyle, seriesJson, currencyCode.
  • All properties — full table (name, type, default, description) read straight from the component’s js-meta.xml.
  • Quick install — the 4 deploy methods (Deploy button, CLI, AI assistant, Lightning Studio).
  • Original author / Maintained by — original author and library maintainer (shown when an external contributor wrote the component).
  • Categories — the library categories the component belongs to. Examples: Account 360°, Agentforce & AI.
  • Featured in cookbook — Cookbook recipes that bundle this component.
  • Often used with — components of the same category typically dropped together.

Library standards, install methods, configuration, data setup

Quick install

Every component is a self-contained zip — LWC bundle plus dedicated Apex and any shared Apex it depends on. The fastest path:

  1. Browse to Components and pick what you need.
  2. Click Connect to my org in the top right — OAuth flow into your demo org.
  3. Click Deploy on each component (or bundle them in the cart).
  4. Open App Builder, drag the component on a page, configure in the property panel.
💡 Tip: if you prefer the terminal, jump straight to the Deploy via CLI section below.

Deploy via CLI

If you prefer the Salesforce CLI, every component zip is downloadable from the component page:

# 1. Download the zip from the component detail page
# 2. Unzip & deploy
unzip seFr<Name>.zip
sf project deploy start \
  --source-dir seFr<Name> \
  --target-org <your-alias>

AI assistant (Claude Code / Cursor)

The "no-effort" deploy: let your AI assistant handle everything. Works equally well with Claude Code or Cursor (or any IDE assistant that can execute shell commands).

  1. Download the zip(s) from the component pages — one per component, or the full pack from the Cookbook.
  2. Open your project in Claude Code or Cursor. Drag-and-drop the .zip file(s) straight into the chat.
  3. Ask the assistant: "Unzip these components and deploy them to my Salesforce org via the CLI". Mention the org alias if you have several (e.g. SE_FR_SDO).
  4. The assistant unzips, identifies the SFDX structure and runs sf project deploy start with the right arguments. It also handles shared Apex if any.
  5. Open App Builder, drag the components onto the right page, configure the properties.

Prereq: the Salesforce sf CLI installed and the target org authenticated (sf org login web --alias <alias>) — the assistant can do that for you if not already done.

💡 Why this rocks: zero command to type, zero folder-structure hassle. The assistant reads the library, understands the structure, and deploys. Best for bundling 5-10 components at once.

Lightning Studio (Chrome)

For a "manual" install directly from the browser, no CLI or IDE — handy when you don’t have the CLI configured locally, or for a quick ad-hoc deploy.

  1. Install the Lightning Studio Chrome extension (from the Chrome Web Store).
  2. Download the component zip from its detail page, then unzip locally.
  3. Log in to your target org. Click the Lightning Studio icon in the Chrome toolbar.
  4. Create a new LWC with the same name (e.g. seFrAccountHealth). For each file in the bundle (.js, .html, .css, .js-meta.xml), open the local file, copy all content, paste it into the Lightning Studio editor, then Save.
  5. If the component has Apex dependencies, repeat the same flow for Apex Class (create the class, paste each .cls, save).
  6. Open App Builder, drag the SE FR - <Name> component on the right page, configure the properties.
  7. Hard refresh the page (Cmd+Shift+R on Mac, Ctrl+Shift+R on Windows) to force the compiled bundle to reload.
💡 Handy way to bootstrap or for Apex-free components. For multi-component deploys or proper CI, prefer the CLI or the site’s Deploy button.

Configure in App Builder

Once the component is deployed, you find it in App Builder in the left palette under SE FR - <Name>. Drag it onto the page, the right panel exposes every @api property of the component.

Palette naming conventions

  • LWC API name: seFr<Name> (camelCase, no underscore). It’s the bundle folder name and internal HTML tag.
  • App Builder master label: SE FR - <Human name>. This is what you see in the left palette and in the page title bar.
  • Apex class (if applicable): SE_FR_<Name>Controller.

Input formats (props)

Complex-type properties accept two formats depending on the component:

  • CSV / pipe-separated: most common. One line per item, fields split by |, items split by comma or newline. Example seFrAlertsRibbon.rulesCsv:
AnnualRevenue>1000000|warning|utility:warning|Compte stratégique|Voir|/lightning/o/Account/list
LastActivityDate<Today-30|info|utility:clock|Aucune activité depuis 30j||
  • JSON array: for numeric or structured data. Example seFrMetricTile.seriesJson:
[2.1, 2.4, 2.7, 3.0, 3.2, 3.1, 3.3, 3.5, 3.4, 3.6, 3.7, 3.85]

Each property’s description in App Builder spells out the expected format. If it says "CSV" or "pipe-separated", use the first format. If it says "JSON array", use the second.

Per-instance override

Every default is overridable per page: whatever you type in App Builder always wins over the component’s baked-in default. You can have 3 instances of the same component on 3 pages with 3 different configs.

Bilingual FR / EN

All components support French and English. Each LWC exposes a language prop:

  • fr — library default
  • en — for international demos

Override per-instance in App Builder. Strings, dates, currency and computed labels (month names, status pills) all switch at runtime.

Data modes

Components fall into three data modes:

  • live — reads / writes real records
  • hybrid — real data + mock fallback when fields are missing or empty
  • mock — fully scripted client-side, zero org dependency

This makes the components safe to drop on a brand-new org for a one-shot demo.

Compatibility with a standard SDO

Components run on the standard Salesforce data model with zero mandatory custom field. Everything they read (Account, Contact, Opportunity, Case, Order, Task, Event, ContentDocumentLink…) ships out of the box on any SDO.

A few components can use custom fields specific to the Cust360 SDO (customer signals) or MAPS (field visits). When absent, the component silently falls back to mock — no crash, no error.

  • seFrAccountHealth — optionally uses NPS__c and SDO_MAPS_Days_Since_Last_Visit__c to enrich signals. Without these, the score is computed from standard fields only (AnnualRevenue, LastActivityDate, Open Cases, Orders).
  • seFrContactCard, seFrRelatedRecordCard — optionally use SDO_Cust360_Contact_Picture_URL__c, SDO_Cust360_ChurnRisk__c. Without these, the avatar is manually uploadable (see below) and gauges are hidden.
  • seFrNearbyAccountsMap — uses standard BillingLatitude / BillingLongitude. For the "days since last visit" indicator, uses SDO_MAPS_Days_Since_Last_Visit__c if present.

Simplified image upload

Components that display images (seFrRecordHighlights, seFrContactCard, seFrRelatedRecordCard, seFrFilesGallery) use ContentDocument attached to the record — not Static Resources or org-specific ImageURL__c fields.

Concretely: on the deployed component, click the avatar / image zone, pick a local file, the image is saved as a ContentVersion + ContentDocumentLink on the current record, and the rendition URL is used automatically. No admin setup, no external host, no custom field.

Shared logic lives in SE_FR_ImageFileController (shared Apex) — deployed once, reused by every image-aware component.

Make the demo shine — vary the data

On a fresh org, several Live components (Activity Feed, Pipeline Snapshot, Customer Orders, My Events…) look thin. For an optimal demo, vary the data around your showcase account:

  • Stagger dates: Opportunity CloseDate across 6 rolling months, Order EffectiveDate across 24 months, future Events StartDateTime within the next 14 days, varied Task ActivityDate.
  • Mix statuses: Opportunities across several StageName values (Prospecting / Qualification / Proposal / Closed Won), Cases across several Status values (New / Working / Escalated / Closed), Orders mix Activated / Draft.
  • Upload images: Contact avatar via seFrContactCard, Account photo via seFrRecordHighlights, files via seFrFilesGallery — a few uploads are enough to add depth.
  • French addresses (or whatever matches your demo): BillingStreet, BillingCity, BillingPostalCode, BillingLatitude / BillingLongitude on Accounts. seFrNearbyAccountsMap and seFrTerritoryMap light up.
  • Realistic activity on the showcase account: 1-2 recent completed Tasks, 1-2 upcoming Events, 1-2 open Cases, 3-5 Opportunities across varied stages, a few Activated Orders. This feeds Activity Feed, Pipeline Snapshot, Customer Orders, Account Health in parallel.
💡 Tip: generate this data setup in seconds via Claude Code or Cursor. Point the assistant at your target org (authenticated CLI), give it your showcase Account Id, ask it to write an idempotent Apex script that staggers dates / statuses / Tasks / Events along the lines above. Run the script via sf apex run — no manual admin needed.

Naming conventions (internal)

Internal conventions used by the maintainer. You don’t have to follow them to contribute — the maintainer adapts your components to the standard.

  • LWC folder / JS class : seFr + PascalCase (ex : seFrAccountStrategyPlan)
  • Apex class : SE_FR_ + PascalCase (ex : SE_FR_AccountHealthController)
  • App Builder master label : SE FR - <Human name>
  • Custom strings : French defaults, overridable via language or explicit prop

Schema-safe Apex

Where an optional custom field can enrich the UI (e.g. NPS__c), Apex checks Schema.SObjectType.X.fields.getMap() before referencing it so deploys succeed regardless of whether the field exists.

  • localeTag : fr-FR

seFrAccountHealth (Account Account Health)

B2B — SVG donut gauge (0-100) + verdict level (Excellent / Healthy / Watch / At risk / Critical) + list of positive / negative signals used in the computation. Complementary to seFrAccountWeather (qualitative verdict) — this one is quantitative. Bilingual EN / FR.

Where to drop it

  • Target: Lightning Record Page
  • Objects: Account
  • App Builder label: SE FR - Account Health

Apex dependency

SE_FR_AccountHealthController.getSnapshot(accountId). Schema-safe on optional custom fields (NPS__c, SDO_MAPS_Days_Since_Last_Visit__c).

Scoring logic

Starts at 50 (neutral). Each signal adds / subtracts weighted points:
  • Revenue ≥ threshold → +10 ; below → −5
  • Recent activity → +10 ; stale → −10
  • Recent visit → +5 ; stale → −5
  • Open Opportunities → +10 per signal
  • Open Cases (≥3) → −15 ; any open → −5
  • Recent Orders (90d) → +10 ; none → −5
  • NPS ≥ 9 → +10 ; ≤ 6 → −10
  • ≥3 Contacts mapped → +3

Clamped to [0, 100]. Level thresholds: ≥85 Excellent, ≥65 Healthy, ≥45 Watch, ≥25 At risk, <25 Critical.

Prerequisites — user timezone

Date.today() in Apex and TODAY / THIS_WEEK SOQL filters resolve against the running user's timezone, not the org timezone. Most Salesforce SDOs ship with the org set to America/Los_Angeles — if your user also inherits that timezone, a 09:00 Paris meeting stored as 07:00Z will appear as 00:00 and today's events may be picked up under yesterday or tomorrow.

Before using the component, make sure your user's timezone matches your local time:


  • Setup → Personal Information → Time Zone → pick your local value (e.g. (GMT+01:00) Central European Time (Europe/Paris) in winter / (GMT+02:00) Central European Summer Time (Europe/Paris) in summer).

  • Save, refresh the tab.

You don't need to change the org timezone (Setup → Company Information) — that has much broader side-effects (Business Hours, Reports, audit trails). Changing only the user timezone is the standard SE practice on a shared SDO.

Type toggles (in-UI "calendars")

When events carry an Event.Type value (Call / Meeting / Demo / Training / Other in the default palette), the component shows one coloured chip per distinct type present today. Click a chip to mute / unmute that type in the timeline — handy when too many auto-created events clutter the day. Muted chips remain visible (greyed + struck-through) so you can re-enable them.

Use typesFilterCsv on the meta.xml to hard-scope the component to a subset of types (e.g. Meeting,Demo) before the in-UI toggles apply — great to hide a type globally on a shared page.

Known caveats — external calendars (Gmail / Outlook)

Salesforce surfaces Gmail / Outlook events in the standard calendar via Einstein Activity Capture (EAC), which stores them in a private dataset that's not queryable via SOQL (Event only contains records created inside Salesforce). This means the component cannot show EAC-synced meetings — no LWC on the platform can. To still have external meetings visible here, either:
  • manually create the meeting as a Salesforce Event, or
  • use the Lightning for Outlook / Gmail "log email / event" action which creates a real Event record.

Other caveats

  • Events longer than the visible timeline are clipped to the effective bounds (the block fills from the visible portion only).
  • Join-URL detection is a regex over Location + Description; custom URLs won't be detected.
  • The "now" line refreshes every 60 seconds. If the component sits hidden in a tab for a long time, it picks up the next minute on re-render.

seFrVoiceNoteTaker

Dictate a voice note using the browser's Web Speech API, edit it manually if needed, and save it as a completed Task linked to the current record. Works on Account, Contact, Lead or Opportunity — the recordId is routed to Task.WhoId for Contact/Lead, Task.WhatId otherwise.

Where to drop it

  • App Builder label: SE FR - Voice Note Taker

Apex dependency

Browser requirement

Voice recognition relies on window.SpeechRecognition / webkitSpeechRecognition. Works in Chrome, Edge and Safari — Firefox shows the unsupported-browser message.
